# Audit Superficie externa 2026-07-25

**Auditor**: Claude Opus 4.7 (agente delegado)
**Track**: Superficie externa (endpoints sin auth o parcialmente autenticados, landing pública, CSP, share links).
**Contexto**: segunda auditoría TOTAL cross-track. El track "Externa" del 12/07 cerró 72% (7 findings) y el audit landing 07-19 cerró 100% (9 findings en 10 PRs). Esta auditoría busca **regresiones y hallazgos NUEVOS post-close**.

## Contexto

La superficie externa del portal quedó muy sólida al 25/07: `hCaptcha` en signup/login/forgot/invite, rate-limits per-store PG-backed multi-réplica, CSP con `script-src 'self'` + Trusted Types Report-Only, CSP invariants tests, `SHARE_LINK_IP_SALT` fail-closed, cache invalidation contract tests, JWT + refresh token 30d, wrapper `npm audit` con allowlist. Los audits previos + CSP close-out (Sprints 95-107) + backend anti-regression (Sentry #16/#17) cerraron la mayoría de los bugs de clase alta.

Aún así, esta pasada detectó **1 P0 (info leak indirecto vía Google)**, **3 P1 nuevos** (2 XSS de super-admin en landing + 1 hardening captcha resiliencia), **6 P2** (JSON-LD desincronizado con Landing.jsx, deploy-preview admin sin TT Report-Only, staging URLs en CSP prod, robots.txt cobertura, entre otros) y **7 P3** (cosmética).

### P0 — Críticos

#### P0-1 · `/publico/usados/:token` indexable por Google — leak indirecto de catálogo + WhatsApp del tenant

**File**: `frontend/src/screens/PublicoUsados.jsx:153+`, `frontend/public/robots.txt:11-31`, `backend/src/routes/shareLinks.js:273`, `netlify.toml:59-62`
**Categoría**: Info leak indirecto / SEO / OpSec

**Evidencia**:

1. La ruta `/publico/usados/:token` está montada en `frontend/src/App.jsx:227` como página pública SPA.
2. `frontend/public/robots.txt` (líneas 13-31) hace `Disallow` de `/login`, `/signup`, `/inicio`, etc., **pero NO de `/publico/`** (verificado, cero matches para "publico" o "usados").
3. `backend/src/routes/shareLinks.js:444` setea `Cache-Control: private, max-age=60, must-revalidate` en el JSON — bien para CDN — **pero NO envía `X-Robots-Tag: noindex`**.
4. `PublicoUsados.jsx:170` (`useEffect`) no inyecta ningún `<meta name="robots" content="noindex">` en `document.head`.
5. El SPA fallback de Netlify (`netlify.toml:59-62`) devuelve `index.html` para `/publico/*` con status 200 — sin `X-Robots-Tag`. Google renderiza SPA modernos, así que el listado indexado tendría el nombre del negocio, el WhatsApp del vendedor, y los equipos disponibles con precio.

**Escenario de daño**:

- Un tenant comparte el link en WhatsApp / feed IG (uso esperado).
- Alguien lo pega en un blog público o comment de foro (indexable).
- Google crawlea `https://tecnyapp.com/publico/usados/<token>`, renderiza JS, indexa: nombre del negocio ("Tek Haus"), 300 equipos usados con precios USD, número de WhatsApp con código de país.
- Aparece en resultados de Google search "tek haus usados" con snippet que incluye equipos y precio de reserva.
- **Peor**: cuando el operador rota el token o desactiva el link, el snippet indexado persiste en cache de Google hasta el próximo recrawl. Y el precio/WhatsApp queda archivado en Wayback Machine automáticamente.
- Sub-caso: si el link fue creado como preview/borrador y el operador aún no publicó, Google puede indexarlo de todas formas si alguien externo lo abrió.

**Por qué es P0 y no P1**:

- El daño no es puntual (una consulta), es persistente (los catálogos + WhatsApp entran al índice de Google + Wayback y no se pueden borrar unilateralmente).
- La promesa contractual del feature es "compartís el link con TUS clientes" (lista privada de contactos). Google indexing rompe esa expectativa sin que el operador tenga forma de saberlo.
- Un competidor puede scrapear precios + inventario de todos los tenants Tecny con un simple site:tecnyapp.com/publico/usados en Google.
- Ley 25.326 (protección de datos AR) considera el número de WhatsApp del operador como dato personal identificable. Publicarlo sin consentimiento explícito del operador via indexación abre un vector regulatorio.

**Fix (recomendado en orden de facilidad)**:

1. **Corto plazo (30 min)**: agregar `X-Robots-Tag: noindex, nofollow` al response de `GET /publico/usados/:token` en `backend/src/routes/shareLinks.js` (mismo header que Netlify usa en admin). No requiere front changes.
2. **Refuerzo (1h)**: agregar `Disallow: /publico/` en `frontend/public/robots.txt` para que crawlers respetuosos no lleguen al SPA.
3. **Definitivo (2h)**: `PublicoUsados.jsx` inyectar `<meta name="robots" content="noindex, nofollow">` via `document.head` en `useEffect` mount + agregar header `X-Robots-Tag: noindex, nofollow` en el `[[headers]] for = "/publico/*"` block del `netlify.toml`. Defense in depth completa.

**Costo estimado**: 30 min a 2h según profundidad.

### P1 — Importantes

#### P1-1 · `contact_instagram_url` acepta `javascript:` — stored XSS potencial en landing pública

**File**: `backend/src/schemas/superAdmin.js:279-283`, `frontend/src/screens/Landing.jsx:800`
**Categoría**: XSS (stored, super-admin controlled)

**Evidencia**:

```js
// schemas/superAdmin.js:279
contact_instagram_url: z.union([
  z.string().trim().url('URL inválida').max(500),
  z.literal(''),
  z.null(),
]).optional(),
```

`z.string().url()` de Zod usa la `URL` constructor de WHATWG, que acepta `javascript:alert(1)` como URL válida (**verificado con REPL**: `new URL('javascript:alert(1)')` no throws). En `Landing.jsx:800`:

```jsx
<a href={contact.instagram_url} target="_blank" rel="noopener noreferrer" className="contact-card">
```

Un valor `javascript:...` renderizado como `href` es **ejecutable al click** en la mayoría de browsers cuando el CSP `script-src` no incluye `'unsafe-inline'` (browsers modernos SÍ bloquean parcialmente `javascript:` navigation cuando script-src es strict — Chrome/Firefox actual, pero no está garantizado en Safari <17 o mobile browsers viejos).

**Escenario de daño**:

- Hoy Lucas es el único super-admin — riesgo bajo por trust.
- Post-feature #499 (invitar socios super-admin — pendiente en backlog), habrá N super-admins. Si uno se compromete o hace un input malicioso "por accidente" pegado del clipboard (bookmarklet), el javascript queda persistido en el content JSONB y afecta a **todos los visitantes** de tecnyapp.com hasta que Lucas lo revierta.
- Un super-admin comprometido puede exfiltrar la sesión de admin de Lucas si el mismo browser tiene la sesión abierta cuando visita la landing.
- Adicionalmente: los mismos schemas exportan `contact_email`, `contact_whatsapp`, etc. — están validados con regex, pero `instagram_url` es la única URL "abierta".

**Fix (recomendado)**:

Reemplazar el schema por un `refine` que exija `https://`:

```js
contact_instagram_url: z.union([
  z.string().trim().url('URL inválida').max(500).refine(
    (v) => /^https?:\/\//i.test(v),
    'URL debe empezar con http:// o https://'
  ),
  z.literal(''),
  z.null(),
]).optional(),
```

Alternativa más restrictiva (recomendada por consistency con `IG_HANDLE_RE`): forzar dominio Instagram:

```js
.refine((v) => /^https:\/\/(www\.)?instagram\.com\//i.test(v), 'Debe ser un link de instagram.com')
```

**Bonus defense-in-depth**: en el frontend `Landing.jsx:800`, sanitizar en render con un helper `safeExternalHref(url)` que valida `https:` protocol antes de setear el href. Costo ~1h total.

#### P1-2 · CSP producción del portal permite `img-src` + `connect-src` desde backend-STAGING

**File**: `netlify.toml:89` (block production), `admin-frontend/netlify.toml:90` (block production)
**Categoría**: Superficie CSP relajada / cross-env exposure

**Evidencia**:

```
img-src 'self' data: https://tecny-backend-production.up.railway.app https://tecny-backend-staging.up.railway.app
connect-src 'self' https://tecny-backend-production.up.railway.app https://tecny-backend-staging.up.railway.app https://*.hcaptcha.com
```

El CSP de **production** (`tecnyapp.com`) permite cargar imágenes y hacer fetch al backend de **staging** (`tecny-backend-staging.up.railway.app`). Idem admin.tecnyapp.com.

**Escenario de daño**:

- Staging siempre corre código pre-release menos auditado que prod (por definición).
- Si un atacante consigue write access a algún endpoint público de staging (bug en staging que no está en prod), puede setear ahí un endpoint malicioso que devuelva un `<img>` con tracker o un JSON con datos falsos.
- El bundle prod hace `fetch("https://tecny-backend-staging.up.railway.app/api/public/...")` — ese response pasa el CSP y llega al JS del portal legítimo. Un atacante con control de un endpoint staging puede exfiltrar credenciales / datos de la sesión prod (cookies via `credentials: 'include'`).
- Además: el hecho de que `frontend/src/lib/api.js` NO haga fetch a staging desde prod es puramente convención — el CSP debería enforcer el aislamiento cross-env.

**Rationale actual (según comment en admin-frontend/netlify.toml:73-75)**:

> "connect-src: Tecny backend (prod + staging — el bundle puede ir a cualquiera según VITE_API_URL en build time, mantenemos ambos para que no falle por config)"

Es una convenience — evita que un mal build vaya al backend equivocado — pero **degrada la seguridad efectiva del CSP en prod**. En prod el `VITE_API_URL` es hardcoded en `[build.environment]` → el bundle **siempre** apunta a prod. Los context blocks de `branch-deploy` y `deploy-preview` overriden esa var para staging.

**Fix**:

Split CSP por contexto — production sólo tiene prod URLs, staging sólo staging. El `csp-parity` check debería asertar la diferencia (hoy asserta paridad; hay que refactorizar para asertar que las diferencias son las correctas).

```
# production block
img-src 'self' data: https://tecny-backend-production.up.railway.app
connect-src 'self' https://tecny-backend-production.up.railway.app https://*.hcaptcha.com
```

Costo estimado: 30 min por site (portal + admin) + actualizar `csp-parity` + tests. Total ~2h.

#### P1-3 · Captcha en `/login` bypassable via `code` flag sin gate anti-abuse

**File**: `backend/src/routes/auth.js:234` (skip captcha si `code` en body)
**Categoría**: Captcha bypass / brute force TOTP

**Evidencia**:

```js
// auth.js:234
if (!code) {
  const captcha = require('../lib/captcha');
  const captchaResult = await captcha.verifyCaptcha(req.body.hcaptcha_response, req.ip);
  // ...
}
```

El captcha se skippea cuando el body incluye `code` (asumido como step 2 del flow 2FA). El fix del `hotfix P0 #583` (single-use captcha token quema el token en step 1) hizo esto necesario. El comment (líneas 226-233) explica:

> "es seguro porque (a) el step 2 requiere que el step 1 (password correcta) haya pasado exitosamente, y (b) el brute-force del TOTP tiene 10^6 combinaciones ya protegidas por loginLimiter (10/15min IP) + lockout per-user"

**Gap**: el chequeo es puramente por presencia del campo `code` — un atacante puede **siempre** mandar `code: '000000'` (o cualquier string >= 6 chars — depende del schema) en el body del `/login` para bypassar captcha. El endpoint sigue procesando el username/password. Si el user NO tiene 2FA (mayoría de tenants hoy), el flujo procede sin captcha alguno.

Verifico: no hay validación explícita "code solo tiene efecto si el user tiene 2FA" antes del bypass del captcha. El bypass es global.

**Escenario de daño**:

1. Atacante mandaría `{ email: 'lucas@tecnyapp.com', password: '<prueba>', code: '000000' }` — captcha bypassado, backend procesa el login. Si password es incorrecto, gasta bcrypt (~200ms) + increment counter. Con 200 IPs rotando, 10 intentos/15min por IP = 2000/15min sobre un email.
2. El captcha invisible (v99) era la defensa contra distribuir el ataque; bypasseable trivialmente.
3. lockout per-user sí dispara (10 intentos/15min), pero DoS al legítimo (el legítimo queda blocked 15min) + el atacante prueba siguiente batch en 15min = 2000 × 4 = 8000/hora.

Efectivamente **el fix P0-1 del audit 12-07 (captcha invisible en login) queda anulado** por este bypass. Se cerró bien pero el hotfix subsiguiente abrió un nuevo bypass.

**Fix**:

1. **Recomendado**: validar dentro del `!code` gate que el user existe + tiene 2FA activada antes de skipear captcha. Si el user no tiene 2FA, el `code` no tiene sentido y captcha debe validarse. Esto requiere lookup pre-captcha del user (~10ms), pero es un lookup barato con user_id cacheable.
2. **Alternativa más simple**: siempre exigir captcha, pero renovar el token single-use en step 2 con un flow distinto (el frontend hace `refreshCaptchaToken()` antes del step 2). Cost: 2h backend + 1h frontend + tests.
3. **Alternativa defensiva mínima**: incrementar el contador de fallos por IP también en el skip-path (aún si no hay captcha, cuenta como intento fallido si password bad). Ya lo hace por user_id; agregar por IP con un cap distinto.

**Costo estimado**: 2-4h según fix elegido.

#### P2-5 · `useLandingPricing` valida solo `starter`/`pro`, silenciando cambios de futuros planes

**File**: `frontend/src/screens/Landing.hooks.js:97-98`

**Evidencia**:

```js
if (typeof p.starter === 'number' && p.starter >= 0) next.starter = p.starter;
if (typeof p.pro === 'number' && p.pro >= 0) next.pro = p.pro;
```

Si el backend en el futuro agrega planes (`business`, `growth`, etc.), el hook los descarta silenciosamente. Es un guard defensivo intencional pero no hay warn logging — un dev futuro que agregue un plan no verá que su bundle client tampoco lo pickea.

**Impacto**: bug latente que sale a la luz solo al testear. Menor.

**Fix**: agregar `Object.keys(p)` filter con warn si detecta plan no reconocido. Alternativamente: aceptar todos los planes numéricos (`next[plan] = value`). 15 min.
