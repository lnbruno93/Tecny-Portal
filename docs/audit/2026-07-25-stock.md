## Findings

### P0 — Críticos

#### P0-1 — `PUT /ventas/:id` canje _existing: UPDATE productos sin `tenant_id` + sin `deleted_at IS NULL`

**File**: `backend/src/routes/ventas.js:383-389`

```js
if (sets.length > 0) {
  params.push(c.producto_id);
  await client.query(
    `UPDATE productos SET ${sets.join(', ')}
      WHERE id = $${params.length}`,
    params
  );
}
```

El SELECT previo (línea 333-338) sí valida `tenant_id = $2 AND deleted_at IS NULL`, pero el UPDATE final NO. Dos consecuencias:

1. **Defense-in-depth roto (mismo patrón que Stock P1-3 anterior)**: si por bug futuro el `SET LOCAL app.current_tenant` se cae (Sentry #16 pattern), un canje edit con `producto_id` de otro tenant podría escribir a un producto ajeno. La tx tiene `SET LOCAL` OK hoy — pero el fix del audit anterior fue exactamente "todo UPDATE explícito filtra por `tenant_id`". Este UPDATE lo saltea.

2. **TOCTOU `deleted_at`**: entre el SELECT (línea 333) y el UPDATE (línea 385), otro proceso puede soft-deletear el producto. El UPDATE lo re-vive con los cambios de canje (clase_id, precio_venta, condicion, proveedor) — rompe la semántica soft-delete sticky. Es exactamente el patrón que la auditoría 07-12 catalogó P2-1 y P0-2 (fixeado en `descontarStock`, `reponerStock`, `PUT /productos`).

**Escenario reproducible**:
1. Venta V con canje que apunta al producto P (id=42, tenant=13).
2. Usuario A abre modal Editar Venta V, cambia la categoría del canje.
3. Usuario B (admin), en paralelo, borra el producto P (soft-delete).
4. Usuario A confirma edit → SELECT falla (producto 42 tiene deleted_at) → `else` en línea 392 → `prodId = null` sin warning. **OK path**.
5. Pero si el orden se invierte (SELECT pasa, DELETE ocurre entre, UPDATE ejecuta) → el UPDATE re-vive el producto con la clase/precio nuevo, dejando `deleted_at` intacto pero pisando otros campos.

**Fix propuesto**: extender el WHERE a `WHERE id = $N AND tenant_id = $M AND deleted_at IS NULL`. Reusar los mismos placeholders que ya están en scope.

**Costo estimado**: 5 min + 1 test regression (mismo patrón que audit anterior).

### P1 — Importantes

#### P1-1 — Doble `className` en `<select>` de filtro Vista (PR #875 regression)

**File**: `frontend/src/screens/Inventario.jsx:1413-1418`

```jsx
<select
  className="input"
  value={vistaFiltro}
  onChange={e => setVistaFiltro(e.target.value)}
  className="u-w-240"
>
```

JSX no permite dos atributos con el mismo nombre. React ignora silenciosamente el primero y warna en dev (`Warning: Duplicate key found in element`). Resultado: el `<select>` solo aplica `u-w-240` — pierde la clase base `input` que aplica altura, borde, padding, tipografía, focus ring, dark mode. Visualmente en prod el select "Vista" ES DISTINTO a los demás inputs de la toolbar (mucho más chico, sin borde consistente).

El bug se introdujo con el PR #875 (filtro Depósito) — antes el select tenía solo `className="input"`. Al agregar el `<label>Depósito</label>` + `<select>` adyacente, se sobrescribió el `className` con el ancho hardcoded en vez de agregarlo con concatenación.

**Fix**: `className="input u-w-240"` en una sola prop.

**Nota**: si el CI corre eslint con `react/no-duplicate-props`, este bug debería haber sido cazado — verificar por qué pasó. Si el rule no está activo, activarlo es una prevención barata.

**Costo estimado**: 2 min fix + 5 min verificar eslint rule.

#### P1-3 — `RecepcionStock.jsx` usa `clase: 'celular'` legacy → productos quedan sin `clase_id`

**File**: `frontend/src/screens/RecepcionStock.jsx:195`

```js
const productos = items.map(it => ({
  ...it,
  deposito_id: deposito_id ? Number(deposito_id) : null,
  proveedor:   proveedor_str,
  clase:      'celular',     // recepción es siempre celulares (los accesorios van por XLSX)
  tipo_carga: 'unitario',
  cantidad:   1,
}));
```

Post-F3.d-3, la columna `productos.clase` VARCHAR **se dropeó** (migration `20260709000001_drop_productos_clase_legacy.js`). El `bulkProductoSchema` acepta `clase` como campo opcional deprecated (para no romper clientes viejos) pero el backend lo **IGNORA** en el INSERT (`PRODUCTO_COLS` no lo incluye — `inventario.js:1186-1192`). Resultado: los productos que RecepcionStock scanea entran a Inventario con `clase_id=NULL`, apareciendo en el filtro "Sin categoría".

Compare con Inventario.jsx (import XLSX) que sí resuelve `clase_id` UUID desde `clases_producto` (línea 262-290 de `importStock.js`).

**Impacto real**: cada tenant que use el flow móvil de Recepción de Stock por escaneo de IMEI (Lucas invitó a Tek Haus a usarlo) tiene productos sin categoría — desalinea la KPI `inv_por_clase[]` del dashboard y rompe el filtro por categoría en Inventario.

**Otro problema adyacente** (líneas 78-137): el select "Categoría *" carga `inventario.categorias()` (Colecciones legacy) y guarda `categoria_id`. Post-audit XLSX Colecciones→Categorías (PR #876), esto es inconsistente — el resto del portal ya migró a Categorías (`clases_producto`) para la clasificación principal.

**Fix propuesto**:
1. Cambiar `mCategoria` a resolver contra `inventario.clases()` (post-F3.a catalog).
2. Reemplazar `clase: 'celular'` por `clase_id: <UUID resuelto>`. Default razonable: la fila base `celular_sellado` del tenant (mismo pattern que `importStock.js` fallback heurístico).
3. Sunset (eventualmente) el hardcode `mCategoria` de Colecciones — o mantenerlo opcional pero clarificar que es dimensión auxiliar.

**Costo estimado**: 1-2h (refactor + tests + verificar 3 test file interactions).

#### P1-4 — `buildBulkMovimientosPayload` silencia reconciliación fallida de clase_id/deposito_id

**File**: `frontend/src/lib/importStock.js:452-458`

```js
if (r._claseNueva && !body.clase_id) {
  body.clase_id = newClaseByName.get(r._claseNueva.toLowerCase()) || null;
}
if (r._depositoNuevo && !body.deposito_id) {
  body.deposito_id = newDepositoByName.get(r._depositoNuevo.toLowerCase()) || null;
}
```

Si `bulkClases` o `bulkDepositos` (backend) devuelven un mapping incompleto (ej. constraint violation en un nombre específico que el frontend no cachó — nombre >80 chars post-trim, colisión con soft-deleted que evita el resolve, etc.), el `.get()` devuelve `undefined` → `|| null` → producto persistido **sin categoría / sin depósito y sin error visible al operador**.

En el flow feliz (backend crea todo lo pedido) esto no ocurre. Pero:
- El backend `POST /clases/bulk` (inventario.js:2038-2094) usa `ON CONFLICT ... DO NOTHING` + un SELECT posterior filtrando `deleted_at IS NULL`. Si hay un nombre marcado `_claseNueva` que **existe soft-deleted** en `clases_producto`, el ON CONFLICT hace nada (partial index excluye soft-deleted) → el INSERT crea la fila nueva. OK.
- Pero si `bulkClasesSchema` (`schemas/clasesProducto.js:80-82`) valida `nombre.max(80)` y el operador escribió "Categoria demasiado larga [80+ caracteres...]", el schema **rechaza toda la request con 400** — bien, el import falla ruidoso. También OK.
- Edge case real: si un nombre tras `.trim().toLowerCase()` matchea otro del mismo lote pero con caps distintas y hay un race condition entre el `INSERT ON CONFLICT` y el `SELECT`... poco probable.

El bug más serio es **cognitivo**: el silence significa que si en el futuro alguien agrega una validación server-side (`checa emoji Unicode`, `check nombre reserved`, etc.) que rechace UN nombre del lote sin fallar la request completa, tenemos productos sin categoría entrando silencioso.

**Fix propuesto**: en `buildBulkMovimientosPayload`, `throw` si `_claseNueva`/`_depositoNuevo` marker existe pero el map correspondiente no tiene el key — mismo patrón que ya usa el helper con proveedor (línea 445-447).

**Costo estimado**: 15 min (2 throws + 2 tests).

#### P1-5 — `GET /inventario/usados` filtro `solo_canjes` no filtra tenant en canje JOIN

**File**: `backend/src/routes/inventario.js:919-934`

El JOIN LATERAL `canjes cj ... WHERE cj.producto_id = p.id AND cj.deleted_at IS NULL` no filtra `tenant_id`. En prod, RLS de `canjes` (heredada por venta → tenant) protege — pero en tests con superuser o si el rol del pool cambiara, un canje de otro tenant podría matchear productos.

Bajo por probabilidad (RLS es el principal freno hoy) pero P1 por consistencia con el patrón del audit anterior (Stock P1-3 defense-in-depth explícito). El LEFT JOIN `ventas v` y `contactos co` que siguen filtran `deleted_at IS NULL` pero también sin `tenant_id`.

**Fix propuesto**: agregar `AND cj.tenant_id = p.tenant_id` (o parametrizado) en el LATERAL. Idem para el LEFT JOIN a `ventas` (`AND v.tenant_id = p.tenant_id`) y contactos.

**Costo estimado**: 15 min + verificar RLS assumptions no rompan tests.

#### P2-7 — `deposito` XLSX: nombre "999" ambiguo (número puro pero no matcheable como ID)

**File**: `frontend/src/lib/importStock.js:313-327`

```js
if (depRaw) {
  if (/^\d+$/.test(depRaw)) {
    const byId = depositos.find(d => String(d.id) === depRaw);
    if (byId) deposito_id = byId.id;
    else depError = `Depósito ID ${depRaw} no existe`;
  } else {
    // Path nombre — auto-create si no matchea
  }
}
```

Si el operador escribe un depósito llamado "999" (nombre puro numérico) en el XLSX, la regex `/^\d+$/` lo trata como ID y busca por ID. Si el ID 999 no existe → error hard "Depósito ID 999 no existe" — el operador **no puede crear un depósito llamado "999"** via XLSX.

Edge case improbable (nadie llama depósitos con solo números), pero el mensaje de error engaña. Considerar: si el operador insiste con nombres puramente numéricos, sugerir en UI + docs que use algún letra ("999A", "D999").

Alternativa técnica: si es número Y no matchea ID, hacer fallback a búsqueda por nombre (matching `d.nombre === depRaw`). Si tampoco matchea, auto-create con nombre "999". Trade-off: pierde detección de typo en ID.

**Fix**: docs + un `hint` en el error message ("Si querés crear un depósito llamado "999", usá un nombre no numérico").

**Costo estimado**: 10 min doc + 1 helper string.
